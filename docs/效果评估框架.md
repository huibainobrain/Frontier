# FrontierLit 评估与迭代体系

## 1. 评估目标

评估只回答三件事：

1. **用户研究任务有没有真正完成？**
2. **如果没完成，问题发生在哪个环节？**
3. **Agent 多做的动态决策，是否带来了足够收益？**

当前重点评估：**结果质量、Agent 过程、效率成本**。真实上线后，再用用户行为验证离线优化是否转化为用户价值。

## 2. 核心指标

| 层级 | 核心指标 | 作用 |
|---|---|---|
| **结果质量** | 任务成功率、需求覆盖率、引用支撑率 | 判断最终任务是否做好 |
| **Agent 过程** | 证据覆盖率、证据缺口识别准确率、重规划增益 | 判断 Agent 在哪里创造价值 |
| **效率成本** | 模型调用次数、Token、响应时延 | 判断质量收益是否值得 |

### 关键口径

| 指标 | 口径 | 评测方式 |
|---|---|---|
| **任务成功率** | 核心需求完成，且无严重事实 / 硬约束错误 | 人工主评，LLM 辅助 |
| **需求覆盖率** | 已满足需求点 / 全部必要需求点 | 需求拆解后核对 |
| **证据覆盖率** | 有有效证据的需求点 / 全部需证据需求点 | 证据格核对 |
| **引用支撑率** | 被 Evidence 支持的事实性结论 / 全部事实性结论 | Claim-Evidence 核验 |
| **证据缺口识别** | Agent 判断的缺口与人工判断是否一致 | 抽样人工复核 |
| **重规划增益** | 重规划后证据覆盖率 - 重规划前证据覆盖率 | 过程记录 + 人工确认 |
| **无效重规划率** | 没有新增有效证据的重规划 / 全部重规划 | 自动统计 + 抽检 |
| **Token / 时延** | 单任务真实模型消耗和端到端耗时 | 自动记录 |

其他过程指标只在出现 Bad Case 时继续下钻，不作为日常核心指标。

## 3. Bad Case 诊断

```text
任务失败 / 需求覆盖不足
        ↓
需求和研究对象理解正确吗？
├─ 否 → 意图 / 对象识别
└─ 是
    ↓
研究规划完整吗？
├─ 否 → Planner
└─ 是
    ↓
关键证据搜到了吗？
├─ 否 → 检索 / 数据源
└─ 是
    ↓
Agent 正确识别证据缺口了吗？
├─ 否 → 证据判断
└─ 是
    ↓
补搜方向正确、且产生新证据了吗？
├─ 否 → Query 改写 / 数据源重选 / Stop 策略
└─ 是
    ↓
已有证据是否被最终答案利用？
├─ 否 → Synthesizer
└─ 是
    ↓
是否仍有无依据结论 / 事实校验误杀？
    → Critic
```

## 4. 指标如何驱动迭代

| 现象 | 初步判断 | 优先排查 |
|---|---|---|
| 需求覆盖↓，证据覆盖也↓ | 前链路没有找到足够信息 | Planner / Retrieval |
| 证据覆盖高，需求覆盖低 | 已经搜到，但最终没写出来 | Synthesizer |
| 重规划触发↑，重规划增益↓ | Agent 过度探索 | Evaluator / Stop 策略 |
| 引用支撑↑，需求覆盖↓ | 事实校验可能过度保守 | Critic 误杀 |
| 质量基本不变，Token / 时延↑ | Agent ROI 变差 | 减少调用 / 按复杂度路由 |
| 规划与重规划正确，但仍无新增证据 | 检索能力成为瓶颈 | 数据源 / 召回策略 |

迭代优先级综合考虑：

> **问题规模 × 用户影响 × 预计收益 ÷ 实现成本**

## 5. 评估怎么执行

当前没有大规模线上用户，不虚构线上流量。Case 主要来自：

> **真实运行 Case + 开发中的真实 Bad Case + 少量定向复杂 Case**

评测分工：

- **程序自动记录**：模型调用、Token、时延、研究轮次、重规划、Retry / Fallback、重复检索；
- **LLM 辅助初评**：需求拆解、需求覆盖、证据缺口、Claim-Evidence 关系；
- **人工重点复核**：复杂 Case、Workflow / Agent 差异明显 Case、Unsupported / Contradicted、高影响 Bad Case。

关键质量结论最终人工确认，避免“模型自己生成、自己证明自己正确”。

## 6. Agent 和模型是否值得

不设置单一“Agent 总分”，统一比较：

> **增量质量 vs 增量成本**

动态重规划重点看：

```text
质量：任务成功 / 需求覆盖 / 证据覆盖 / 重规划增益
成本：模型调用次数 / Token / 响应时延
```

模型升级同样遵循这一原则。当前使用免费层 API 是开发阶段的成本选择；后续可在同一流程下比较不同模型或分级路由策略：

```text
关键判断节点的质量提升
vs
新增 API 成本 / Token / 时延
```

如果复杂任务或关键节点使用高阶模型有明显收益，再考虑定向升级，而不是默认全链路使用最高成本模型。

## 7. 当前已具备与上线后扩展

**当前已具备**

- Workflow / Agent 消融开关；
- 不同评测任务独立存储与调用日志；
- 模型调用、Token、时延、研究轮次、重规划和停止原因记录；
- Critic / Citation 结构化结果；
- 真实 Case 过程 Trace。

**真实上线后再补**

- Query 二次改写率；
- 引用点击 / 展开；
- 收藏 / 保存；
- 同类研究任务复用；
- 正式线上 A/B 与长期留存。

当前作品集重点展示 **评估体系设计、过程可观测和真实 Bad Case 驱动的迭代方法**，不展示未经验证的大规模效果数字。
