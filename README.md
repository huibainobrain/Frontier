# FrontierLit

> 面向前沿 AI 动态追踪与复杂研究的智能研究 Agent：从用户研究目标出发，完成多源检索、证据判断、动态补搜与可追溯输出。

## 1. 为什么做这个产品

我长期需要跟踪 AI 模型、Agent、工具链和头部实验室的新进展。实际过程中，信息分散在实验室官网、论文平台、RSS 和开源社区；当问题从“找一篇资料”变成“比较两个团队、追踪一项技术、补齐多个研究维度”后，传统搜索的使用成本明显上升。

我把问题进一步拆成三类：

- **信息分散**：同一主题需要跨多个官方 / 学术来源反复搜索；
- **证据不完整**：一次检索容易出现某些对象或维度覆盖充分、另一些明显缺失；
- **结果不够可信**：生成答案可能遗漏关键维度，或出现“有引用，但引用并不真正支持结论”。

因此设计 FrontierLit，希望把“反复搜索 → 判断还缺什么 → 补搜 → 整理 → 核验”的人工研究过程产品化。

## 2. 从问题到产品

| 阶段 | 核心判断 | 产品动作 |
|---|---|---|
| **发现问题** | 复杂研究不是单纯“搜不到”，而是需要持续判断信息是否充分 | 定义比较、追踪、摘要、阅读路径四类核心任务 |
| **搭建 MVP** | 先验证多源检索 + 结构化研究能否完成基本任务 | 接入官方源、arXiv、Semantic Scholar、OpenAlex 等来源 |
| **Agent 化** | 固定流程无法处理运行中出现的证据缺口 | 引入“规划 → 证据判断 → 动态重规划 → 定向补搜” |
| **持续迭代** | Agent 多做一步不代表更好，需要判断收益是否值得 | 增加长期记忆、事实校验、运行观测和评估体系 |

工程实现过程中使用 Claude 等 AI Coding 工具加速落地；我主要负责 **问题定义、需求拆解、Agent 架构、模块边界、Prompt / 数据结构、验收标准和迭代方向**。

## 3. 核心产品场景

| 场景 | 示例 |
|---|---|
| **横向比较** | 比较 OpenAI 与 Anthropic 在 Agent Memory 上的方案 |
| **演进追踪** | 追踪某项 Agent 技术从 2025 到 2026 的变化 |
| **主题摘要** | 汇总某一时间段最值得关注的 Agent 进展 |
| **阅读路径** | 为某一主题生成有先后关系的学习计划 |

## 4. 核心产品链路

复杂任务并非固定执行“搜索一次 → 生成答案”，而是：

```text
用户需求
  ↓
研究规划
  ↓
多源检索 → 内容分析
  ↓
证据充分度判断
  ↓
证据足够？
  ├─ 是 → 综合生成
  └─ 否 → 识别证据缺口 → 改写 Query / 重选数据源 → 定向补搜
  ↓
事实校验
  ↓
最终回答
```

外层 Workflow 控制研究轮次、文章预算、去重和失败隔离；Agent 只负责运行时无法完全预定义的判断。

## 5. 一个真实运行 Case

一次 OpenAI vs Anthropic 的比较任务中：

```text
Round 1
初始规划 + 多源检索
        ↓
发现部分维度证据不足
        ↓
判断是否值得继续研究
        ↓
Round 2
针对缺口改写 Query，并收窄数据源
        ↓
补充证据后停止
```

该次任务实际运行 **2 轮研究**，系统同时记录模型调用、Token、时延、重规划状态和停止原因。

我更关注的不是“Agent 多搜了一轮”，而是：

> **这一轮是否补到了真正缺失的证据，以及质量收益是否值得额外成本。**

## 6. 关键架构决策

| 问题 | 选择 | 原因 |
|---|---|---|
| 固定流程还是 Agent | **Agentic Workflow** | 研究路径需要根据中间证据动态调整，但成本和停止边界仍需确定性控制 |
| 是否全 Multi-Agent | **中央编排 + 局部 Agent 决策** | 当前任务主要是串行研究，没有强独立协商需求 |
| 长期记忆怎么做 | **SQLite + Chroma 的持久化 RAG** | 历史研究持续增长，不适合全部塞入上下文 |
| 如何控制无依据结论 | **规则校验 + 语义事实校验** | 结构问题适合规则，证据是否真正支持结论需要语义判断 |

详细取舍见：[架构决策](产品架构决策.md)。

## 7. 评估与迭代

FrontierLit 不只评最终答案，也评 Agent 的过程决策和额外成本。

| 层级 | 核心指标 | 回答的问题 |
|---|---|---|
| **结果质量** | 任务成功率、需求覆盖率、引用支撑率 | 用户任务有没有真正完成 |
| **Agent 过程** | 证据覆盖率、证据缺口识别、重规划增益 | Agent 在哪里创造或损失价值 |
| **效率成本** | 模型调用次数、Token、响应时延 | Agent 收益是否值得额外成本 |

```text
真实 Case → 评测 → Bad Case 归因
→ 产品 / Prompt / 检索 / Agent 策略调整
→ 回归验证
```

核心原则：**不追求单一“Agent 总分”，而是比较质量增益与成本增量。**

详细口径见：[评估与迭代体系](效果评估框架.md)。

## 8. 模型与成本策略

当前处于产品验证和作品集阶段，受调用成本限制，主要使用 **免费额度 / 免费层 LLM API** 完成开发与验证，仅在内部实验测试Token消耗ROI时使用过付费层模型。

模型调用层按任务节点做了分层和配置隔离，因此产品链路并不绑定当前模型：

- 可直接通过模型 / API 配置切换更高阶 LLM；
- 不需要重写 Agent 主链路；
- 后续可按任务价值进一步采用“简单节点低成本模型、关键判断高阶模型”的分级策略。

因此当前版本重点验证的是 **产品逻辑、Agent 架构和评估方法**，而不是把免费模型的绝对效果当作系统能力上限。

## 9. 当前实现

- **Agent / 编排**：Google ADK + Gemini
- **检索**：OpenAI / Anthropic / DeepMind / Hugging Face 等官方公开源 + arXiv / Semantic Scholar / OpenAlex
- **长期记忆**：SQLite + Chroma
- **可靠性**：统一重试、失败隔离、全局文章预算、跨轮去重、零证据硬停止
- **事实校验**：真实引用 → Evidence → Claim 校验；发现无依据结论后触发修订
- **运行观测**：记录真实模型调用次数、Token、时延、研究轮次和停止原因
- **协议扩展**：检索能力可通过 MCP 对外暴露；A2A 仅作为互操作实验，不进入核心研究链路

代码同时保留单轮 Workflow / Agentic Workflow 两种模式，用于比较复杂任务下动态重规划的真实收益。

## 10. 本地运行

Python 3.11。

### 方式 A — `uv`（如果已安装）

```bash
uv venv --python 3.11
source .venv/bin/activate
uv pip install -e ".[dev]"
cp .env.example .env
# 在 .env 中配置当前使用的模型 API Key / Model
pytest tests/
```

### 方式 B — `pip`（不依赖 `uv`，任意装了 Python 3.11 的机器都能跑）

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -e ".[dev]"
cp .env.example .env
# 在 .env 中配置当前使用的模型 API Key / Model
pytest tests/
```

## 11. 当前限制

- 部分 RSS / sitemap 仍以轻量关键词相关性为主；
- 由于此前免费测试过程中遇到部分测试用户大规模烧Token，因此除内部实验优化Token消耗ROI外，在GitHub的public版本上主要使用免费层模型，复杂推理上限受模型能力影响；
- 免费层 API 在高峰时段偶尔会持续触发限流（429）或服务不可用（503），即使内置了退避重试，个别请求仍可能长时间失败——这是 Google 侧的配额 / 稳定性问题，不代表 Agent 逻辑本身有错，建议稍后重试；
- 尚未完成大规模真实用户评测和线上 A/B。
